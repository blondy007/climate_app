# Cierre de la segunda campaña de lluvia · 04/11/2026

**Resultado: fallo operativo de inicialización. Cero observaciones y cero emisiones.
La campaña está cerrada; no aporta evidencia para aprobar ni descartar el método.**

## Hechos comprobados en la VPS

La comprobación de fuente del 30/10 a las **11:00:07 UTC (12:00:07 CET)** pasó:
DBZH 10:45/10:50/10:55, RATE 10:45, con cobertura local completa y edades
aproximadas de 15/10/5 y 15 minutos. Ambos lugares pudieron emitir en ese sondeo.
Por tanto, este cierre **no se atribuye a falta de lluvia ni a fuente inadecuada**.
El sondeo preparatorio no sustituye las predicciones de una campaña prospectiva.

Docker lanzó `climate-radar-capture-20261030` a las **11:00:08 UTC**. El código
original creó `live-config.json`, pero falló antes del primer ciclo al leer
`/data/live-budget.json`: **PermissionError [Errno 13]**. El archivo había sido
creado por el orquestador como `root:root`, modo `0600`, debido a `UMask=0077` de
systemd. El colector se ejecuta como `1000:1000` y no podía leerlo. La carpeta era
correctamente propiedad de UID 1000; el fallo estaba en el archivo previamente
sembrado. Es un error del arranque preparado para esta campaña, no del algoritmo.

Se agotaron **cinco reinicios automáticos** y el contenedor terminó con salida
**1 el 30/10/2026 a las 11:00:38.320 UTC**, sin OOM. La lectura del 04/11 confirmó:

- **0 recortes de radar**, **0 archivos de emisiones**, sin `live-status.json`
  ni `prospective-report.json`. No hubo un ciclo de captura efectivo.
- Presupuesto conservador sembrado: **750.000.000 bytes reservados** para pruebas;
  permaneció intacto. No significa 750 MB descargados ni disco ocupado.
- Datos de investigación medidos antes del diagnóstico: **14.227 bytes**.
- Imagen, motor, límites y montajes originales conservados; sin puertos publicados.
- SHA-256 del motor: `5e8e4205924afd7c9514b9de5d851cd63ed53e90ec87b9046867ac68eacd952e`.
- El temporizador de cierre se ejecutó el **02/11 a las 11:00:00.286 UTC** y no
  necesitó detener nada porque el contenedor ya estaba finalizado.

`docker start` y el servicio systemd devolvieron éxito aunque el proceso Python
falló inmediatamente después. El recibo `started.json` acredita lanzamiento,
no captura efectiva. Las pruebas previas de orquestación no detectaban la
interacción entre la umask de systemd y el UID real del contenedor.

## Consecuencia científica

La ventana completa de 72 horas tuvo cero emisiones de captura. No existen
pares comparables con persistencia, referencia posterior, falsas alarmas o
aciertos evaluables. **CSI/POD/FAR y precisión con lluvia no son estimables**;
no se registran como cero ni se interpreta la ausencia de datos como tiempo seco.
La auditoría de pares no se ejecuta sobre una colección inexistente.

No se descargó radar histórico ni se generaron predicciones a posteriori para
rellenar esta campaña. No se necesitó consultar CHS para este diagnóstico: un
pluviómetro cercano tampoco podría recuperar predicciones que nunca se emitieron.
No se afirma si llovió o cuánto en el punto urbano durante el periodo perdido.

## Corrección verificada y conservación

Se corrigió **solo el orquestador del repositorio de investigación**: el presupuesto
nuevo se entrega a UID/GID 1000 conservando modo privado `0600` y creación
exclusiva. También se exige confirmar la inicialización del colector antes de
registrar un arranque correcto. No se instala esta corrección sobre la campaña
vencida ni se cambian sus permisos, presupuesto, plazos o código congelado.

**Nueve pruebas de seguridad pasan**, incluidas umask estricta, no sobrescribir
presupuesto, no presentar éxito de Docker como inicialización y no reabrir sesiones.
Además se reprodujo el recorrido real en Linux ARM64 con la imagen científica,
UID 1000 y un presupuesto creado por root bajo umask 0077: lectura, escritura de
estado y cierre sintético verificados. El contenedor de prueba no tenía red y
su ciclo se sustituyó por un fixture vacío; no fue una captura meteorológica.

Se restauraron **11 archivos de metadatos** de esta campaña en una carpeta
independiente y se verificaron hashes. No hay recortes nuevos que restaurar.
Es una prueba parcial de conservación del diagnóstico, no una recuperación
completa de plataforma ni una validación de predicciones.

Las evidencias se conservan en `radar-lab-20261030/final-review-20261104`, dentro
del volumen ya incluido en el backup integral. Se deshabilitan únicamente los
dos temporizadores vencidos de esta campaña y se retira su heartbeat. La campaña
anterior, SQLite, cuentas, credenciales y la aplicación pública quedan fuera de
esta operación. No se publica la funcionalidad ni se cambia `oracle-production`.

## Decisión

**Cerrar esta campaña como fallida por inicialización. Mantener la función sin
publicar y el resultado científico inconcluso.** Una nueva campaña necesitaría
nueva autorización, otra ventana lluviosa y comprobación real de inicialización
con el UID y la umask finales antes de esperar al episodio. No se programa una
tercera campaña, no se amplían recursos y no se rellena retrospectivamente la
ventana perdida.

[primera campaña](2026-10-26-final.md). Evidencia primaria: estado Docker,
metadatos de sondeo, permisos, logs acotados de arranque y recibo del temporizador.
